# Telegram rich results and TravelLine room content

Research date: 2026-08-08. Sources are limited to the official Telegram Bot API, the official TravelLine OpenAPI specifications/documentation, and the local TravelLine MCP source.

## Executive conclusion

- **Confirmed:** Telegram now has a first-class feature officially named **Rich Messages**. Its Markdown input mode is named **Rich Markdown style** and is sent through `sendRichMessage` as `InputRichMessage.markdown`. This is different from regular `sendMessage(parse_mode="MarkdownV2")`.
- **Confirmed:** Rich Markdown directly supports `**bold**`, `*italic*`, `[link text](https://...)`, standalone media blocks, and `<tg-slideshow>`/`<tg-collage>`. A rich message may contain up to **50 media attachments in total**.
- **Confirmed:** The older `sendMediaGroup` album accepts **2–10 media items**. This ten-item ceiling is not the Rich Message ceiling.
- **Confirmed:** TravelLine Search API availability results contain prices, meal information, room/rate identifiers, occupancy text, availability, and a nullable `bookingFormLink`; they do **not** contain room names, room descriptions, amenities, or room images.
- **Confirmed:** TravelLine Content API separately exposes room category name, description, amenity codes, area, occupancy and image resource URLs. These records can be joined to Search API results by room type ID.
- **Baseline before implementation:** `agent-simth-travelline` called only Search API and exposed neither room names nor actual room descriptions, amenities, area or images. The implementation described below adds Content API enrichment and a batch details tool.
- **Not confirmed without an authenticated real-property call:** whether the configured hotel's Content API records are populated, how many images each room has, whether every returned image URL is anonymously reachable with a Telegram-compatible MIME type and size, and whether `bookingFormLink` is populated for these credentials.

## 1. Telegram formatting: official names and syntax

### Confirmed: regular messages

For a regular `sendMessage`, Telegram calls the feature simply **Formatting options**. A bot can provide explicit message entities or select one of these `parse_mode` values:

- `MarkdownV2`: bold is `*bold*`, italic is `_italic_`, and a text link is `[Забронировать](https://example.com/)`.
- `HTML`: bold is `<b>bold</b>`/`<strong>`, italic is `<i>italic</i>`/`<em>`, and a text link is `<a href="https://example.com/">Забронировать</a>`.

Official source: [Telegram Bot API — Formatting options, MarkdownV2 and HTML](https://core.telegram.org/bots/api#formatting-options).

Important implementation distinction: ordinary Markdown generated by an LLM often uses `**bold**`; that is **not** Telegram MarkdownV2's bold syntax. MarkdownV2 also requires escaping many punctuation characters. If the transport remains `sendMessage`, either render trusted HTML safely or convert/escape model Markdown deliberately.

### Confirmed: Rich Messages and Rich Markdown

Telegram introduced **Rich Messages** in Bot API 10.1 (2026-06-11) and later added explicit rich-message media mapping in Bot API 10.2 (2026-07-14). A rich message is sent with [`sendRichMessage`](https://core.telegram.org/bots/api#sendrichmessage). `InputRichMessage` must use exactly one of `markdown`, `html`, or explicit `blocks`: [official object schema](https://core.telegram.org/bots/api#inputrichmessage).

The Markdown mode is officially named **Rich Markdown style**. Relevant syntax is:

```markdown
**Название категории**
*25 000 ₽ — без завтрака*
Краткое описание, адаптированное под запрос гостя.
[Забронировать](https://example.com/booking)
```

This syntax is documented in [Rich Message Formatting Options](https://core.telegram.org/bots/api#rich-message-formatting-options). Telegram describes Rich Markdown as compatible with GitHub Flavored Markdown where possible.

`sendRichMessage` also accepts `reply_markup`, including `InlineKeyboardMarkup`. Therefore, if product UX prefers a real button rather than an inline text link, a URL button labelled **«Забронировать»** is supported by the same API method. A Rich Markdown inline link also works.

### Confirmed: Rich Message media and slideshow

Rich Markdown media must be a separate block, for example `![](https://host/image.jpg)`. Media blocks accept only HTTP/HTTPS URLs, and Telegram determines the media type from the URL and MIME type. The documented slideshow wrapper is:

```markdown
<tg-slideshow>

![](https://host/room-1.jpg)
![](https://host/room-2.jpg)

</tg-slideshow>
```

Official examples and constraints: [Rich Markdown media, collages and slideshows](https://core.telegram.org/bots/api#rich-message-formatting-options).

The published Rich Message limits are up to 32,768 UTF-8 text characters, 500 blocks, 16 nesting levels and **50 media attachments in total**: [Rich Message limits](https://core.telegram.org/bots/api#rich-message-limits).

### Not confirmed/documented

- The official Bot API page does not state a separate per-`<tg-slideshow>` item limit. The documented hard limit is 50 media attachments across the whole Rich Message. Therefore, “maximum 10 images in a Rich Message/slideshow” should not be encoded as a Telegram requirement.
- Client-version fallback behaviour for recipients using a Telegram client too old for Bot API 10.1 Rich Messages was not documented in the reviewed source. This should be tested before relying on Rich Messages as the only production delivery path.

## 2. Classic `sendMediaGroup` albums

### Confirmed

[`sendMediaGroup`](https://core.telegram.org/bots/api#sendmediagroup) sends an album of photos, live photos, videos, documents or audio. Its `media` array must contain **2–10 items**. Documents and audio can only be grouped with messages of the same type.

Each [`InputMediaPhoto`](https://core.telegram.org/bots/api#inputmediaphoto) may contain:

- an optional caption of 0–1024 characters after entity parsing;
- `parse_mode` or explicit `caption_entities`, so bold/italic/text links are possible in a caption;
- a `media` value that is a Telegram `file_id`, an HTTP URL Telegram fetches, or an uploaded attachment.

`sendMediaGroup` itself has no `reply_markup` parameter. Consequently, an inline keyboard button cannot be attached directly to the album call; the booking action must be an inline URL in a media caption or a separate message/button. By contrast, `sendRichMessage` does accept `reply_markup`.

Telegram can fetch a public image URL itself; the bot does not have to download the image first. For URL delivery, Telegram documents a 5 MB maximum for photos and requires a correct MIME type. See [Sending files by URL](https://core.telegram.org/bots/api#sending-files).

### Practical interpretation

- If using classic albums, cap one album at 10 photos and expect a separate textual result message or carefully selected caption.
- If using Rich Messages, use `<tg-slideshow>` and the 50-media total limit, subject to client compatibility testing.
- Public URL support is confirmed, but a TravelLine URL must still be checked for anonymous access, redirects, MIME type and image size.

## 3. TravelLine Search API availability response

### Confirmed by the official Search API OpenAPI schema

The endpoint used by the MCP is `GET /api/search/v1/properties/{propertyId}/room-stays`. Its response contains `DetailedRoomStay` items. See the [official Search API OpenAPI document](https://partner.tlintegration.com/api/search/swagger/v1/swagger.json) and the [human-readable TravelLine API reference](https://www.travelline.ru/dev-portal/docs/api/).

Useful search-result fields include:

- `roomType.id` and `roomType.placements`;
- `ratePlan.id`;
- `availability`;
- `currencyCode`, `dailyRates`, `total` and taxes;
- `cancellationPolicy`;
- `includedServices` and `mealPlanCode`;
- `fullPlacementsName`, documented as a string description of accommodation/guest placement;
- `availableDiscounts` and `extraServicesAvailable`;
- nullable `bookingFormLink`.

The official schema describes `bookingFormLink` as a direct link to the hotel's official booking form containing the parameters for the current rate, but says it is **specified only for metasearch partners**. It must therefore be treated as optional rather than assumed present.

The Search API `DetailedRoomType` object contains only room type ID and placement entries. The availability response does **not** define room-category `name`, marketing `description`, amenities, room area, occupancy summary, or images.

### Not confirmed

- Whether this production integration is entitled as a metasearch partner and receives non-null `bookingFormLink` values. The current code assumes the field is present, but no authenticated request was made for this research.
- Whether the Search API returns extra undocumented fields for this account. The implementation should depend on the official schema or explicitly tolerate provider extensions.

## 4. TravelLine Content API: names, descriptions, characteristics and images

### Confirmed by the official Content API OpenAPI schema

The separate Content API exposes property content through `GET /api/content/v1/properties/{propertyId}`. In its `roomTypes[]`, the `RoomTypeInfo` schema provides:

- `id` and `name`;
- nullable detailed `description`;
- nullable `amenities[]` containing amenity codes;
- nullable `images[]`, whose `Resource` objects contain a `url`;
- `size.value` in square metres;
- category code/name, address, occupancy, placements and display position.

See the [official Content API OpenAPI schema](https://partner.tlintegration.com/api/content/swagger/v1/swagger.json) and TravelLine's [Content API content guide](https://www.travelline.ru/support/knowledge-base/content-api-opisanie-obektov-razmeshcheniya/). TravelLine's guide also says the image order received from Content/Search APIs should be preserved because the hotelier controls it.

Rate plans are also content records: `ratePlans[]` include an ID, name and nullable description (which may contain HTML). Amenity display names can be obtained from the Content API's amenity dictionary rather than showing raw codes.

Therefore the intended result card is technically achievable by joining:

- Search API `roomType.id` -> Content API `roomTypes[].id` for category name, description, amenities, area and images;
- Search API `ratePlan.id` -> Content API `ratePlans[].id` for rate name/description;
- Search API price, meal, cancellation, availability and booking link for the selectable offer.

### Not confirmed

- Content completeness is controlled by the hotelier; nullable fields may be empty.
- The OpenAPI schema calls each image value a “resource link” but does not guarantee in the schema that every URL is publicly reachable by Telegram, has a Telegram-compatible MIME type, or is below Telegram's URL-fetch size limit.
- The number of room images per category is not bounded in the reviewed TravelLine schema.

## 5. What the current TravelLine MCP actually returns

### Confirmed from local source

The MCP tool's exact unprefixed name is `search_available_rooms` (`/Users/mikegeine/Work/agent-simth-travelline/booking_plugin.py:77-81`). The host Agent Smith may add an MCP-server namespace when exposing tools to the model; that composed name depends on the registered server/tool naming logic and should be verified in the runtime tool list before hard-coding the fully qualified name in a skill.

The current client calls only the Search API room-stays endpoint (`travelline_client.py:76-122`). It does not call Content API.

`_format_room_stay` currently exposes (`booking_plugin.py:47-74`):

- `room_id`, `rate_plan_id`;
- `description = fullPlacementsName`;
- meal plan, price, loyalty price, currency and tax;
- cancellation fields, rooms left/low-availability, payment method;
- `booking_link = bookingFormLink`.

It does **not** expose:

- room/category name;
- actual room marketing description;
- rate-plan name/description;
- amenity names/codes, room area or occupancy metadata;
- any image URLs.

The existing tool docstring explicitly tells the agent that official category name and photos are unavailable and must not be invented (`booking_plugin.py:116-120`). That statement is accurate for the current MCP payload, but not a limitation of TravelLine's APIs as a whole: Content API can supply those fields.

### Required data change for the proposed UI

Before instructing the agent to render rich cards with names and photos, extend the MCP payload with nullable, explicitly sourced fields such as:

```json
{
  "room_name": "Standard",
  "room_description": "...",
  "room_size_m2": 25,
  "amenities": [{"code": "wifi_internet", "name": "Wi-Fi"}],
  "image_urls": ["https://..."],
  "rate_plan_name": "Room only",
  "rate_plan_description": "...",
  "booking_link": "https://..."
}
```

Content can be cached by property/content revision or with a bounded TTL because it changes much less often than availability. Search prices and availability must remain request-time data. The MCP should preserve TravelLine's image order and safely handle null/absent content and booking links.

## Verification boundary

This note confirms schema capabilities and current local implementation only. It does not prove that the configured production hotel has populated content, that its credentials are authorized for Content API or metasearch booking links, that every image works through Telegram's fetcher, or that the deployed Telegram client/library stack already supports Bot API 10.1/10.2 Rich Messages. Those require an authenticated TravelLine call plus an end-to-end Telegram test.
